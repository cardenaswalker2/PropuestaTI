Propuesta de Modernización de Arquitectura Tecnológica

Transición del Sistema de Control de Cambios FADM36-1 hacia Aplicación de Escritorio Windows (Flutter) conservando la Infraestructura de Datos en Microsoft 365 y Automatizaciones en Power Automate

🏢 Entidad y Contexto

Ajover Darnel S.A.S.
Sistema de Gestión Integral (SGI)
Procedimiento FADM36-1 (v1.5)

🎯 Objetivo Estratégico

Evolucionar la experiencia de usuario y rendimiento mediante Flutter Desktop en Windows, preservando listas de SharePoint y flujos de notificación.

👥 Audiencia de Decisión

Dirección de Área, Jefatura de Proyecto, Departamento de TI, Administradores de M365 y Seguridad Informática.

Principio Rector de la Propuesta: No se propone descartar ni destruir la infraestructura existente. La iniciativa busca optimizar la interfaz operativa en puestos de trabajo Windows mientras se mantiene el 100% de la gobernanza, datos en listas SharePoint y flujos automáticos ya testeados.
Diagnóstico

Resumen de la Situación Actual y Motivación

Por qué evaluar una aplicación nativa de escritorio frente al aplicativo Power Apps existente

Actualmente, la compañía opera el proceso FADM36-1 (Versión 1.5) para administrar el ciclo de vida de los cambios (fases de Planeación, Desarrollo y Finalización). Si bien la solución en Power Apps ha centralizado la información de manera efectiva, la operación diaria en planta y oficinas presenta oportunidades de mejora significativas:

⏱️

Tiempos de Carga en Navegador

Power Apps web requiere descargar pesados paquetes JavaScript y metadatos de sesión en cada arranque, generando latencias perceptibles en computadores de planta u oficinas con ancho de banda compartido.

🧩

Complejidad en Fórmulas Power Fx

Los archivos de pantalla (ej. PantallaCreacionSolicitud.yaml y PantallaDetallesPropuestaCambioNUEVA.yaml) superan los 800 KB de fórmulas combinadas en bloques OnSelect, dificultando el mantenimiento y versionamiento en Git.

🖥️

Experiencia de Usuario de Escritorio

Una aplicación de escritorio Windows nativa (Flutter C++) ofrece renderizado a 60-120 FPS mediante Impeller/Skia, atajos de teclado fluidos, apertura instantánea e integración con el sistema operativo sin depender de pestañas de navegador.

🔒

Gobierno de Licenciamiento

Evaluar si la operación a mediano plazo requerirá conectores premium o capacidades offline, y cómo estructurar el acceso para no incurrir en sobrecostos inesperados de licencias de Power Platform.

Mecanismo de Autenticación en Windows (Punto Crítico)

En Flutter Desktop para Windows no es viable ni seguro utilizar webviews móviles convencionales ni guardar credenciales/secretos en el código. La solución técnicamente respaldada por Microsoft y compatible con Windows es el flujo OAuth 2.0 Authorization Code con PKCE (Proof Key for Code Exchange):

  • Inicio de Sesión: La aplicación abre el navegador predeterminado del sistema (ej. Microsoft Edge) contra el endpoint de autorización de Microsoft Entra ID. Esto aprovecha automáticamente las credenciales corporativas (Single Sign-On - SSO), MFA por Microsoft Authenticator y directivas de Acceso Condicional de la empresa.
  • Retorno del Código: Flutter levanta un listener HTTP local transitorio (ej. http://localhost:4200/auth-callback) o registra un Custom Protocol URI (ej. ajover-cambios://auth) para capturar el código de autorización de forma segura.
  • Protección del Token: El token de acceso y refresh token se almacenan cifrados en el equipo local utilizando Windows Data Protection API (DPAPI) a través del plugin flutter_secure_storage, garantizando que ninguna otra aplicación o usuario sin privilegios pueda leerlos.

Responsabilidades y Ventajas de la Capa Backend

1. Centralización de Reglas

El algoritmo de cálculo del riesgo (promedio de áreas × factor de consecuencia) reside en Java. Si Calidad o Seguridad Industrial cambian las fórmulas normativas, solo se actualiza el backend sin tocar los computadores de los usuarios.

2. Blindaje de Permisos

Los usuarios no requieren permisos directos de escritura en las listas de SharePoint. El backend valida el rol de proponente o aprobador y ejecuta la escritura mediante una identidad de servicio controlada.

3. Trazabilidad y Auditoría

Registro inmutable de quién intentó modificar una solicitud, IP de origen, cambios de estado y control contra operaciones duplicadas (idempotencia).

4. Desacoplamiento de Servicios

Flutter solo conoce endpoints REST estandarizados (ej. /api/v1/cambios). Si en el futuro SharePoint se complementa o migra, el frontend permanece intacto.

Modelos de Autenticación y Autorización del Backend

Modelo de Acceso Mecanismo Técnico Ventajas Principales Riesgos y Aprobación de TI
Modelo 1: Permisos Delegados (On-Behalf-Of - OBO) El backend intercambia el token JWT recibido del usuario de Flutter por un nuevo token de Graph API en nombre de ese colaborador específico. Garantiza que la auditoría en SharePoint refleje exactamente al usuario que ejecutó la acción. Respeta al 100% los permisos del usuario en M365. Mayor complejidad de configuración en Microsoft Entra ID. Requiere registrar tanto la API como la App cliente con consentimiento consentido.
Modelo 2: Identidad de Aplicación (Client Credentials / Managed Identity) El backend se autentica contra Graph API con su propio secreto o Managed Identity usando el permiso acotado Sites.Selected. Arquitectura más robusta y desacoplada. Los empleados no necesitan permisos directos sobre la lista de SharePoint, previniendo accesos accidentales vía Excel/Web. Aprobación de TI indispensable: Debe limitarse el acceso exclusivamente al sitio de SharePoint del proceso mediante Sites.Selected para que el backend no sea una puerta abierta al tenant general.
Infraestructura y Nube

Evaluación de Despliegue: Render vs. Microsoft Azure

Análisis riguroso de seguridad, costos, administración y viabilidad de aprobación por el área de TI

Servicios de Microsoft Azure en Evaluación

Para una organización como Ajover Darnel que ya opera su ecosistema corporativo en Microsoft 365, SharePoint y Entra ID, Microsoft Azure ofrece una integración nativa y alineada con las políticas corporativas:

  • Azure App Service (Linux) o Azure Container Apps: Permite desplegar el contenedor Docker de Spring Boot con escalado automático, soporte oficial de Java 17/21 y health checks nativos.
  • Azure Managed Identity (Identidad Administrada): Elimina la necesidad de almacenar secretos, contraseñas o llaves de API en archivos de configuración. La instancia se autentica de forma transparente contra Entra ID.
  • Azure Key Vault: Central de almacenamiento cifrado (FIPS 140-2) para cualquier secreto o certificado que el backend requiera.
  • Azure Monitor & Application Insights: Telemetría en tiempo real, latencias de endpoints REST, rastreo de excepciones y auditoría de ciberseguridad integrada con Microsoft Defender for Cloud.
  • Aprobación de TI: Alta Viabilidad No requiere incorporar un nuevo proveedor externo ni gestionar facturaciones separadas. Se incluye en el contrato de suscripción Enterprise / CSP existente.

Análisis del Despliegue en Render

Render es una plataforma como servicio (PaaS) moderna y eficiente para startups y desarrollo ágil. A continuación se detallan sus condiciones operativas:

  • Configuración Docker: Requiere un Dockerfile multi-stage estándar con OpenJDK 17 Eclipse Temurin.
  • Limitaciones del Plan Gratuito: Inviable para producción empresarial. La instancia se "duerme" tras 15 minutos de inactividad, tardando más de 50 segundos en responder (cold start), lo cual arruinaría la experiencia en las plantas de Ajover Darnel.
  • Instancia Requerida: Para producción con Spring Boot 3 se requiere mínimo el plan Standard (2 GB RAM, 1 CPU) con un costo de $25 USD/mes para garantizar tiempos de respuesta estables y sin reinicios por OutOfMemory.
  • Veredicto de Seguridad y TI: Riesgo de Rechazo por TI El departamento de TI generalmente veta el envío de tokens corporativos o procesamiento de datos internos a través de un tercero fuera del perímetro de confianza de Microsoft sin acuerdos formales de BAA o auditoría SOC2 corporativa aprobada.
Criterio de Evaluación Render Cloud Microsoft Azure (Container Apps / App Service)
Alineación con el Ecosistema Plataforma aislada de terceros. Requiere crear y gestionar credenciales externas. Nativa con Microsoft 365, Entra ID, SharePoint y Power Platform.
Seguridad de Credenciales Variables de entorno estáticas con Secret Keys de Entra ID. Azure Managed Identity (Cero secretos en código) + Azure Key Vault.
Latencia hacia SharePoint Rutas a través de internet público hacia los endpoints de Graph. Tráfico optimizado por la red troncal (backbone) de Microsoft.
Facilidad de Aprobación por TI Baja (Requiere auditoría de compliance y nuevo vendor). Alta (Proveedor homologado y gobernanza bajo el mismo tenant).
Costo Mensual Estimado $25 USD/mes (Plan Standard). ~$45 - $58 USD/mes (App Service B2 o Container Apps dedicado).
Integración de Notificaciones

Estrategia de Integración con Power Automate, Gmail y Teams

Cómo conservar las automatizaciones actuales sin reconstruirlas desde cero y adaptarlas a la nueva aplicación

Reutilización de Flujos Actuales: El Reto del Trigger

Como se detectó en la auditoría, los flujos clave (ej. Copia de: Enviar Correos Creación de propuesta Cambio y Copia de: Momento Cerrado) inician con el trigger manual Request (PowerAppV2). Este trigger está diseñado para responder a llamadas de la función .Run() de Power Apps y no puede invocarse directamente desde Flutter por protocolo estándar.

Solución A: Desencadenador por Evento de SharePoint (Recomendada)

Modificar el trigger del flujo para que se active automáticamente con:
When an item is created or modified en la Lista de Procesos Control de Cambios vrs 1.5.
Ventaja: Funciona idéntico si el cambio se hace desde Flutter, desde Spring Boot o incluso desde SharePoint. Cero acoplamiento con la interfaz de usuario.

Solución B: Desencadenador HTTP Request (Webhook Seguro)

Cambiar el trigger a When a HTTP request is received.
Ventaja: Permite que el backend Spring Boot o Flutter envíen un payload JSON para disparar el flujo al instante.
Requisito TI: Este conector requiere validación de licenciamiento de Power Automate y seguridad de la URL de callback.

Prevención de Notificaciones Duplicadas y Bucles

Al utilizar triggers automáticos en SharePoint (When an item is modified), existe el riesgo de que el flujo se ejecute múltiples veces al guardar adjuntos o actualizar campos. Para evitar correos duplicados y sobrecostos de ejecuciones, se deben implementar las siguientes directivas oficiales:

  • Condiciones de Activación (Trigger Conditions): Configurar en el flujo expresiones de filtro como: @equals(triggerOutputs()?['body/MomentodelCambio/Value'], 'Planeación') para que solo se dispare cuando el estado cambie específicamente.
  • Bandera de Control (Control Flag): Añadir una columna booleana en SharePoint como CorreoEnviado = Sí/No para asegurar que la notificación se procese exactamente una vez (idempotencia).
  • Conectores Gmail vs. Outlook: Si se requiere Gmail para ciertas cuentas contratistas o externas, validar que la cuenta de conexión sea compartida institucional (Service Account) y no personal, cumpliendo con las políticas DLP de Power Platform del tenant.
Ciberseguridad y Gobernanza

Seguridad Informática y Requisitos para el Área de TI

Arquitectura de defensa en profundidad, privilegios mínimos y matriz de responsabilidades

Identidad y Acceso (Entra ID)

Autenticación basada estrictamente en Microsoft Entra ID. Compatibilidad total con políticas de Autenticación Multifactor (MFA) y Acceso Condicional para dispositivos administrados.

Permisos Acotados (Sites.Selected)

No se solicitarán permisos globales (como Sites.FullControl.All). Se empleará Sites.Selected, otorgando acceso de lectura/escritura únicamente a la colección de sitios de Control de Cambios.

Cero Secretos en el Cliente

El binario de Flutter para Windows se distribuye como un cliente público (Public Client Application), sin secretos embebidos ni contraseñas. Los tokens se cifran localmente con Windows DPAPI.

Políticas de Prevención DLP

Todas las operaciones de datos se mantienen dentro del tenant de Microsoft 365, respetando las políticas de Data Loss Prevention establecidas por el equipo de seguridad.

Decisión Estratégica

Propuesta de Arquitectura Recomendada para Ajover Darnel

Estrategia evolutiva en dos etapas: Eficiencia de costos inmediata con escalabilidad garantizada

Recomendación Principal: Implementar la Arquitectura A (Flutter Desktop + SharePoint + Power Automate con triggers por evento) como fase inicial. Esta alternativa ofrece la mayor relación costo-beneficio, eliminando costos recurrentes de servidores, conservando la base de datos de SharePoint intacta y requiriendo una menor fricción de aprobación ante el departamento de TI.

Por qué esta es la mejor decisión para la empresa:

  1. Cero Gasto de Servidores: No se requiere contratar instancias en la nube (evitando gastos innecesarios en Render o Azure para un volumen de 25-50 cambios mensuales).
  2. Aprovechamiento Integral de Microsoft 365: Los datos residen en las listas ya existentes (Lista de Procesos Control de Cambios vrs 1.5 y Definiciones Riesgo | Análisis 4 que).
  3. Continuidad de Flujos: Los flujos de Power Automate continúan operando para notificar por correo institucional y Teams al cambiar el estado del ítem en SharePoint.
  4. Camino de Escalabilidad (Arquitectura B como Fase Futura): Si en el futuro el volumen de transacciones se multiplica o la empresa decide implementar lógica de integración con SAP u otro ERP, el frontend Flutter ya estará construido y solo requerirá redirigir sus endpoints hacia un backend Spring Boot alojado en Microsoft Azure (descartando Render por razones de gobernanza).

Argumentos de valor, respuestas a objeciones y discurso ejecutivo estructurado

A. Discurso Ejecutivo de Presentación (2 - 3 Minutos)

"Buenos días. El objetivo de esta propuesta no es desechar ni cambiar lo que ya funciona bien en la empresa. El procedimiento FADM36-1, las listas de SharePoint y los flujos de Power Automate han demostrado su valor en ordenar el control de cambios. Sin embargo, en el día a día, los colaboradores en planta y oficinas experimentan tiempos de carga y limitaciones de interfaz inherentes a una aplicación web en navegador.

Nuestra propuesta plantea modernizar la interfaz hacia una aplicación de escritorio nativa para Windows desarrollada en Flutter. Esto nos entrega una herramienta rápida, profesional y con la identidad de Ajover Darnel, manteniendo al 100% la infraestructura de datos en SharePoint y las notificaciones existentes. Demostramos además que con la Arquitectura A el costo adicional de servidores es cero, utilizando los permisos delegados de Microsoft 365. Con esto elevamos la calidad percibida del sistema, eliminamos la fricción de usuario y garantizamos total tranquilidad de seguridad para el departamento de TI."

B. Banco de Respuestas a Posibles Objeciones

Power Apps resolvió la primera fase del proyecto con éxito. Sin embargo, su código YAML actual supera los 800 KB con lógicas sumamente complejas que dificultan el mantenimiento. Además, Flutter Desktop ofrece apertura instantánea en Windows, operación a 60 FPS sin recargar navegador y una experiencia de usuario personalizada sin el consumo de memoria del navegador web.

No. En la Arquitectura A recomendada, el costo recurrente de infraestructura es de exactamente $0 USD mensuales, pues se conecta directamente a SharePoint Online con las cuentas de Microsoft 365 ya contratadas. Además, evita el riesgo financiero de requerir licencias Power Apps Premium ($20 USD/usuario/mes) si el proceso demandara capacidades avanzadas.

Esa fue precisamente una de las razones para recomendar la Arquitectura A: no requiere Render ni ningún servidor externo. Y en caso de que a futuro se requiera un backend en Spring Boot, la propuesta establece que se alojará en Microsoft Azure bajo el contrato corporativo existente, garantizando total cumplimiento de seguridad.

En absoluto. Las plantillas HTML de correo (azul institucional) y la lógica de envío se conservan intactas. El único cambio es técnico y toma menos de una hora: migrar el disparador de PowerAppV2 a When an item is created/modified en SharePoint, haciendo que el flujo se ejecute automáticamente sin importar desde dónde se guardó la información.
